# SkyDeck dev plan

The full phase plan for SkyDeck, as of 2026-11-07. SkyDeck is meant to become Sri's own take on a full-featured flight tracker app, built for the web. It is independent: it uses its own name, code and visuals and is not affiliated with any commercial app. `roadmap.md` lists only the phases still planned; the README describes what exists today.

## How to read this plan

**Status**

- **Done**: merged into `dev`.
- **Open**: planned for the first public release, not started.
- **Needs decision**: waiting on a choice from Sri (listed in "Decisions needed").
- **Post-release**: deliberately after the first public release (Phase 24 and later).
- **Not planned**: considered and left out.

**Three questions for every feature**, so a feature never depends on data we do not have:

1. What does the user see?
2. What data does it need, and where does it come from?
3. What does the user see when that data is missing?

**Source verification levels** used in the data-source table:

- **Tested**: I made one real request on 2026-11-07 and saw the result (status, format, CORS header).
- **Docs/search**: seen in official documentation or search results only. Not tested, and the terms were not read in full.
- **None found**: no free source was found.

Terms were not fully read for any source. Read each source's terms before building on it (as was done for OpenSky, airplanes.live and Airframes).

**Where the feature ideas come from.** The feature list for later phases comes from public descriptions of an iOS flight tracker app (its App Store listing, release notes and one partner video), gathered through research notes. These are advertised features, not tested ones, and none were verified by using that app.

## Ground rules

- Free only: no paid services. Free tiers are fine, but every feature must degrade gracefully when a free quota runs out.
- **A backend is now allowed** (the earlier "no backend, no keys" rule was dropped on 2026-11-07). Secrets live only in server-side environment variables, never in the repo, the browser bundle or the README. `.env` files stay out of git.
- Live ADS-B data goes through the server proxies. Airframes ACARS stays browser-direct and on demand until the legal review and the Airframes answer are in (see Phase 6).
- OpenSky is not a provider and stays out without a written licence.
- No new dependencies without asking. No edits to `src/components/ui/*`.
- Map overlays must be re-installed in the `style.load` handler.
- The stack stays React 19 + TypeScript (TanStack Start). The repo is already all `.ts` and `.tsx` (104 files, no plain JavaScript in `src`), so no conversion phase is needed.
- Phone, tablet and desktop must all work (check 1280, ~746 and 375 px).
- Educational and hobby use only: no navigation, flight planning or safety claims.
- AGENTS.md still carries the old no-backend wording and must be updated (with Sri's approval) when Phase 18 starts.

## Numbering note

The original plan had five phases: 1 live map, 2 glide and reach, 3 message inspector, 4 airports, 5 personal features. The ACARS card was later labelled "Phase 4a" in local plan files and PR history, which clashed with the original Phase 4 (airports). This plan keeps Phases 1 to 5 and moves ACARS to **Phase 6** (the built card is 6a; it was called "4a" before). Weather and the other feature areas continue from Phase 7. Because a backend is now allowed, **Phase 18** (backend foundation) is added and comes before the backend-dependent features. Foundation and operations phases added later also have numbers: 18 backend, 19 scale and data pipeline, 20 real-time experience, 21 operations, 22 app polish, 23 community and help. The number order is not the build order (see Suggested order).

**Decided 2026-11-07 (AI): two providers, Gemini first and Cloudflare Workers AI as the fallback.** The server hides both behind one small "AI provider" interface: try Gemini first, and when Gemini returns its rate-limit or daily-cap error (or the server's own counter says the cap is reached), switch to Workers AI for the rest of that period. Each provider has its own budget counter, so the free pools add up. Sri will supply a Gemini API key. It is kept only as a server-side secret (a Cloudflare secret in production, an uncommitted local file in development): never pasted into chat, issues or pull requests, and never committed. Gemini's free limits must be read from Google's own pages before building (sources disagree). Free-tier prompts may be used by the provider, so no message text goes to Gemini until that is checked. If it is not acceptable, Workers AI becomes the only provider for message text. The cache is shared, so the provider that produced a summary is stored with it.

How AI would be used so free quotas are enough:

- **On demand only** (a button), never automatic for every message or flight.
- **Cache every result** in the database, keyed by the message or flight, so each item is summarised at most once.
- **Daily budget cap** in the server: when the free pool is used up, show the rule-based text instead and say so.
- **Always labelled "AI-generated"**, with the original text one click away.
- **Fallback**: Phase 6c (rule-based explanations) works with no AI at all.
- Message text sent to an AI provider counts as sharing it with a third party; review that in the ACARS legal review.

## Phase 20: Real-time experience

New. Goal: motion that looks continuous and live, like the commercial trackers: a few seconds of deliberate delay, but no gaps, jumps or aircraft that freeze and then snap.

Why it needs a deliberate delay: today the browser polls every 7 s and moves each aircraft forward by dead reckoning (speed and track), then corrects with an easing step when the next poll arrives. Extrapolating forward is a guess, so planes drift, snap or freeze when data is late. If the display instead shows the world a few seconds in the past, every point on screen sits between two real samples, so it can be interpolated and never guessed. The price is latency: the display runs about one and a half sample intervals behind the data. The sample interval is the lever: with 7 s polling the delay would be about 10 s, with a faster shared feed (Phase 19) it can drop to roughly 3 to 5 s. These numbers are targets to test, not measured. The data itself (receivers, aggregator, our provider) already carries some seconds of delay that we cannot remove, and no source is guaranteed to be gap-free.

| Phase | Work                                                                                                                                                                                                                                                                      |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 20a   | Sample buffer: keep the last samples of every aircraft with their true timestamps (the provider's age of position, not our arrival time), instead of only the latest.                                                                                                     |
| 20b   | Delayed renderer: draw every aircraft at "now minus delay" by interpolating between its two surrounding samples (position, altitude, heading, speed). Dead reckoning is used only past the newest sample, capped to a few seconds, and then the aircraft is marked stale. |
| 20c   | Adaptive delay: measure how late samples really arrive (jitter, skipped polls) and set the delay to cover it, with a floor and a ceiling; a "Live / Smooth" setting lets the user trade latency for smoothness.                                                           |
| 20d   | Gap handling: an aircraft missing from one or two updates stays on screen and keeps moving along its last heading, then fades out after a time limit with its "last seen" age shown; no sudden vanishing and reappearing.                                                 |
| 20e   | Push instead of poll: the server sends changes to the browser as they arrive (server-sent events or a WebSocket through a Durable Object) from the shared tile cache, instead of every visitor polling. Cuts latency and requests; depends on 19b and 19c.                |
| 20f   | Change-only updates: send only aircraft that changed since the last update, with compact fields, to keep bandwidth small at faster refresh rates.                                                                                                                         |
| 20g   | Clock alignment: estimate the offset between browser and server clocks so timestamps compare correctly, and tell the user the current delay (for example "Live, 8 s behind") in the status chip.                                                                          |
| 20h   | Consistent panel and trails: the selected aircraft's panel values, trail and glide ring come from the same delayed moment as its icon, so numbers and picture agree.                                                                                                      |
| 20i   | Pan and zoom without holes: prefetch the tiles around the view and keep a short buffer for them, so moving the map does not show an empty area while data loads.                                                                                                          |
| 20j   | Tests and metrics: simulated feeds with jitter, dropped updates and late packets; count visible jumps, freezes and gaps; a small debug overlay with delay, buffer length and update age.                                                                                  |
| 20k   | Reuse the buffer for session replay (9a) and for the 30-day replay design (9b).                                                                                                                                                                                           |
